# 정책 상태 영구 저장

`/policy` API는 SQLite를 사용합니다. 서버 재시작·프로세스 재생성 후에도 아래 상태가 유지됩니다.
번들 조회의 ETag/304 동작은 동일합니다. 초안 저장과 발행의 동시 수정 보호는
[정책 초안 API](policy-draft-api.md)를 참고하세요.

| 저장 대상 | 테이블·동작 |
| --- | --- |
| 배포한 정책 | `policy_bundle`: 버전, DSSE 서명 봉투, SHA-256, 저장 시각, 규칙 수 |
| 마지막 적용 정책 | `policy_active`: 적용 버전·시각, 규칙, 유형 설정, 임계값 등 |
| PC 적용·거부 기록 | `policy_ack`: 기기, 버전, 상태, 사유, 수신 시각을 모두 기록 |
| 최신 모델 매니페스트 | `model_manifest`: 서명한 DSSE 봉투 |
| 서명 키 식별 정보 | `policy_signing_key`: 공개키만 저장. 개인키는 DB에 저장하지 않음 |
| 미배포 정책 초안 | `policy_draft`: payload, 변경 목록, 수정 번호·시각·처리자, 기준 발행 버전 |

다음 배포 버전은 저장된 배포·적용 버전 중 최댓값 + 1입니다. 버전 할당·서명·저장을 하나의
SQLite 쓰기 트랜잭션으로 처리하므로 여러 서버 프로세스가 같은 DB에 동시에 배포해도
중복 버전이 생기지 않습니다. 서명·DB 저장 실패 시 버전과 상태를 변경하지 않습니다.
재시작 후에도 이전 버전의 `/policy/deploy`는 `rollback`으로 거부합니다.

PC 기록은 이력으로 보존하되 기존 집계 기준을 유지합니다. `/policy/acks`는 기기별 마지막
수신 기록, `?version=N`과 `/policy/N/acks`는 해당 버전의 기기별 마지막 수신 기록을 셉니다.
수신 순서는 DB 행 ID 기준이므로 오래된 버전의 ack가 늦게 도착해도 기존 API와 동일하게 동작합니다.

## 경로와 운영 설정

| 환경 변수 | 로컬 기본값 | 제공하는 systemd 유닛 |
| --- | --- | --- |
| `POLICY_DB_PATH` | 저장소의 `data/policy.db` | `/var/lib/ibalance/policy.db` |
| `POLICY_KEYS_DIR` | 저장소의 `keys/` | `/var/lib/ibalance/keys/` |

`LOG_DB_PATH`와 별도로 설정합니다. `data/`, `keys/`는 Git에 포함하지 않습니다.
systemd의 `StateDirectory=ibalance`가 서비스 사용자 소유의 `/var/lib/ibalance`를 만들고,
디렉터리 권한은 `0700`입니다. 컨테이너에서는 DB와 키 경로를 모두 영구 볼륨에 연결하세요.
모든 서버 워커가 같은 로컬 SQLite 파일과 키 디렉터리를 사용해야 합니다. 여러 호스트에서
네트워크 파일시스템으로 SQLite를 공유하는 구성은 이 변경의 대상이 아닙니다.

앱 시작 시 필요한 테이블을 만들고 저장된 상태를 그대로 사용합니다. DB 오류를 빈 저장소로
대체하지 않으므로 손상·권한 오류는 시작 또는 요청 실패로 드러납니다. `PolicyStore.reset()`은
테스트용 메모리 저장소에만 허용합니다. 실제 DB나 키를 지우면 기록·버전·신뢰 관계를 복구할 수 없습니다.

## 기존 서버를 새 경로로 옮길 때

**기존 개인키와 `trust/` 전체를 먼저 보존해야 합니다.** 키를 새로 만들면 직원 PC가 이미
신뢰하는 공개키와 달라집니다. 기존 시스템이 다른 `POLICY_KEYS_DIR`을 사용한다면 그 경로를 기준으로 옮기세요.

1. 기존 메모리 방식 서버가 아직 실행 중이면 `/policy/latest`, `/policy/history`와
   `/policy/{version}`, `/policy/model/latest`에서 보관할 번들을 먼저 확보합니다.
   기존 메모리에만 있던 데이터를 이 변경이 자동으로 가져오지는 않습니다. 과거 ack 개별 행은
   기존 API가 집계만 제공하므로 자동 복구할 수 없습니다.
2. 서비스를 중지한 상태에서 기존 키 디렉터리를 `/var/lib/ibalance/keys`로 복사합니다.
   이미 SQLite 저장을 사용했다면 기존 `policy.db`도 보존해 새 위치로 옮깁니다.
   실행 중인 DB는 단순 파일 복사 대신 SQLite 백업 API를 사용하세요.
   대상 경로에 파일이 이미 있으면 덮어쓰지 말고 동일한 DB·키인지 먼저 확인합니다.
3. 소유자를 서비스 계정 `ubuntu`, 상태·키 디렉터리를 `0700`, 개인키를 `0600`으로 설정합니다.
   키를 보존한 후 새 systemd 유닛을 설치하거나 동일한 환경 변수를 기존 유닛에 추가하고
   `systemctl daemon-reload` 후 재시작합니다.
4. `/policy/history`, `/policy/current`, `/policy/acks`, `/policy/model/latest`를 확인합니다.
   기존 메모리 방식에서 처음 전환하여 DB가 비었다면, 확보한 마지막 유효 서명 번들을
   `/policy/deploy`로 적용하여 버전 기준을 복구한 뒤 새 정책을 발행합니다.
   이때 다음 버전은 복구한 적용 버전보다 커집니다. PC의 최종 적용 버전보다 낮은 번들로
   복구하면 충분하지 않습니다. 오래된 번들의 만료·조직·모델 검증도 그대로 수행합니다.

저장소의 `deploy.sh`는 기존 설치된 systemd 서비스를 재시작할 뿐 유닛 파일을 교체하지 않습니다.
따라서 새 경로 적용은 위 초기 이전 작업에서 한 번 수행해야 합니다. 이후 DB·키가 같은
경로에 남아 있으면 코드 체크아웃을 교체해도 정책 상태가 유지됩니다.
메모리 방식 시절의 이전 전체 이력은 자동 복원되지 않으며, 복구한 번들은 적용 상태·버전
기준으로 사용됩니다. 새로 발행하는 정책부터 영구 배포 이력에 쌓입니다.

## 서명 키 유지와 장애 처리

- 새 키는 최초 생성 시에만 만들며 개인키 파일 권한은 `0600`입니다. 키 생성은 Linux/macOS의
  파일 잠금으로 여러 프로세스 사이에서도 직렬화하고, 파일은 원자적으로 교체합니다.
- 개인키는 있고 공개키 파일만 없다면 동일 개인키에서 공개키를 복원합니다.
- 공개키만 남았거나 키 파일이 손상·불일치하면 새 키를 임의로 만들지 않습니다.
- DB는 최초 서명 공개키를 기억합니다. 이후 키 파일 전체가 사라지거나 다른 정상 키 쌍으로
  바뀌어도 정책·모델 배포는 `503`으로 실패합니다. DB에 저장된 정책과 버전은 그대로 유지합니다.
- 이 경우 DB와 짝이 맞는 **원래 개인키 및 신뢰 공개키**를 백업에서 복구해야 합니다.
  의도적인 키 회전과 직원 PC의 신뢰 키 배포는 별도 운영 절차입니다.

후속 버전 증가를 확인합니다. 4개 프로세스의 동시 발행, 서로 다른 DB에서의 동시 최초 키 생성,
