# 탐지 전처리 적용 평가

2026-11-05. 기존 규칙 보강이 적용된 동일 작업 트리와 로컬 AEGIS ONNX 모델을 기준으로, 전처리 적용 전후를 비교했다. 기존 600문장은 탐지·가명화·재검사까지 실행했다.

## 방식

원문은 그대로 검사한다. 전각 숫자 또는 숫자 사이 특수 하이픈·보이지 않는 문자가 있으면 숫자 검사 사본을 만들고 추가 검사한다. 사본의 탐지 구간은 문자 위치 대응표로 원문 구간으로 변환해 원문 결과와 합친다. 보이지 않는 문자는 숫자 문맥에서만 제거한다. 원문과 사본의 서로 다른 유형이 겹쳐 모호하면 기존 가명화 오류 처리가 적용된다.

## 기존 평가 데이터

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 전처리로 내용이 바뀐 문서 | — | 1/600 |
| 전체 파이프라인 완료 | 598/600 | 598/600 |
| 주민등록번호 전체 구간·유형 탐지 | 117/146 | 117/146 |
| 외국인등록번호 | 65/87 | 65/87 |
| 카드번호 | 94/135 | 94/135 |
| 계좌번호 | 72/98 | 72/98 |
| 사업자번호 | 12/26 | 12/26 |
| API 키 | 25/30 | 25/30 |
| 비밀번호 — 한국어 | 23/26 | 23/26 |
| 비밀번호 — 비밀정보 | 13/30 | 13/30 |

전화번호(182/188), 이메일(194/194), IP(84/85)도 전후 동일했다. 한국어·비밀정보 표본에서 각각 1건씩 `PseudonymError`가 발생했다. 주석이 없는 문서 중 어떤 유형이든 탐지된 문서는 한국어 13/30, 비밀정보 12/30으로 전후 동일했다. 주석이 없다고 실제 음성으로 검증된 것은 아니므로 이 값을 오탐률로 해석할 수 없다.

## 합성 표기 변형 사례

전화번호·ID·카드·사업자번호를 정상 표기, 전각 숫자, 특수 하이픈, 숫자 내부의 보이지 않는 문자로 변형한 양성 16건과 사람 검토 전의 합성 음성 18건을 사용했다.

| 항목 | 원문 검사만 | 통합 탐지기 |
|---|---:|---:|
| 정답 전체 구간·유형 탐지 | 8/16 | 16/16 |
| 정답 위치만 정확히 마스킹 | 7/16 | 16/16 |
| 대상 유형 경고가 난 음성 초안 문서 | 0/18 | 0/18 |
| 탐지시간 중앙값 | 6.58ms | 12.46ms |
| 탐지시간 p95 | 9.62ms | 16.36ms |

시간은 양성 16건을 각 3회 실행한 총 48회 기준이다. 변형이 있는 입력은 원문과 사본을 각각 검사하므로 모델 추론이 두 번 실행된다. 소규모 표본의 시간은 제품 전체 지연시간을 대표하지 않는다.

## 한계

- 16건 합성 사례는 전처리 대상 형식을 의도적으로 포함한다. 독립적인 한국어 업무 문장과 사람이 확인한 정상 데이터에서 성능과 오탐을 다시 측정해야 한다.
- 이번 변경은 전처리만 비교했다. 계좌·카드 등 기존 미탐과 두 문서의 가명화 오류는 해결됐다고 볼 수 없다.
- 숫자가 아닌 문맥의 제로폭 문자와 하이픈은 그대로 둔다. 문자 정규화는 언어별 의미를 바꿀 수 있어 추가 범위 확대에는 별도 검증이 필요하다.
- 실행 중인 테스트 서버는 코드 변경 이전 프로세스이므로 새 기능을 시험하려면 재시작해야 한다. 재시작 시 진행 중 세션의 메모리 매핑은 사라진다.
