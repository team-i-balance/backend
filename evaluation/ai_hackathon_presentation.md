# iBalance 4조 — 로컬 개인정보 탐지·가명화 (발표용 요약)

> 한 줄 요약: AI에 입력하기 전 텍스트를 로컬 규칙과 ONNX 모델로 검사하고, 탐지된 개인정보를 작업별 가명으로 치환하는 MVP를 구현했다.
>
> 범위 구분: 로그 수집·큐 분류·집계·암호화 export는 백엔드 로그 모듈 담당이다. 이 문서는 그 앞단의 로컬 탐지·가명화 기능을 설명하며, 두 모듈의 API 통합은 아직 완료되지 않았다.

## 1. 큰 그림

```text
[사용자 입력]
   → 로컬 테스트 화면
   → 규칙 탐지 + 로컬 ONNX 문맥 탐지
   → 작업별 가명 치환 (원문 매핑은 메모리에만 보관)
   → 가명화된 텍스트 재검사
   → 사용자가 결과 확인
   → (데모) 가상의 AI 응답에 있는 허용된 가명 복원
   → 작업 종료 시 매핑 폐기
```

- 실제 외부 AI 호출은 연결하지 않았다. 테스트 화면의 복원 단계는 AI 응답을 직접 붙여 넣는 시뮬레이션이다.
- 원문과 가명 매핑은 서버 프로세스 메모리에서 작업별로 관리한다. API 키·토큰·비밀번호는 응답에서 자동 복원하지 않는다.

## 2. 구현한 AI 모듈

위치: `backend/local_ai/`

| 파일 | 역할 |
|---|---|
| `detector.py` | 형식이 분명한 정보의 로컬 규칙과 선택형 AEGIS ONNX 추론, 탐지 구간 병합 |
| `pipeline.py` | 탐지 → 가명 치환 → 가명화 결과 재검사 |
| `pseudonym.py` | 작업별 메모리 매핑, 반복값 가명 일관성, 안전한 복원·종료 |
| `__main__.py` | 로컬 CLI 실행 |
| `README.md` | 설치와 실행 안내, 지원 범위 및 제한 |

### 탐지 방법

- **규칙 기반:** 전화번호·이메일, 사업자번호 검증숫자, API 키 설정문·일부 제공자 패턴을 검사한다.
- **문맥 모델:** AEGIS Token Classification ONNX 모델을 로컬 CPU에서 실행해 이름·주소·ID·카드·계좌·IP 등 문맥이 필요한 항목을 보완한다. 모델 파일은 앱 실행 시 인터넷에서 내려받지 않는다.
- 모델과 규칙 결과는 시작·끝 문자 위치와 유형으로 합친다. 겹치는 유형이 모호하면 잘못 치환하지 않고 작업을 실패 처리한다.
- 사업자번호의 현재 제품 규칙은 검증숫자를 요구한다. API 키는 현재 지원하는 키 이름과 토큰 형식에 한계가 있다.

## 3. 평가 방법

평가 스크립트: `evaluation/evaluate_secret_rule_candidates.py`

| 데이터 | 문장 수 | 구성 |
|---|---:|---|
| 한국어 개인정보 표본 | 510 | 여러 공개 출처에서 샘플링, CC BY 4.0 |
| 비밀정보 표본 | 90 | 합성 API 키 30, 비밀번호 30, 비민감 예시 30; CC BY-NC 4.0 |
| **합계** | **600** | 주석 구간 1,045개 |

- 정답 구간과 탐지 구간이 일부만 겹치는 경우는 성공으로 세지 않았다. 정답 문자의 **전부를 허용된 탐지 유형이 덮을 때만** 성공으로 계산했다.
- 이는 정답 구간 기준의 엄격한 탐지율(재현율)이다. 모든 오탐을 수동 판정한 음성셋이 없어 정밀도와 F1은 산출하지 않았다.
- 모델·데이터셋 파일 해시, 출처별 결과, 실패 건수를 기록한다. 평가 파일에는 원문과 탐지값을 출력하지 않는다.

## 4. 현재 탐지 성능 — 모델 + 기존 규칙

| 유형 | 전체 구간 탐지 |
|---|---:|
| 전화번호 | 182/188 · 96.8% |
| 이메일 | 194/194 · 100% |
| 주민등록번호 | 117/146 · 80.1% |
| 외국인등록번호 | 62/87 · 71.3% |
| 카드번호 | 94/135 · 69.6% |
| 계좌번호 | 72/98 · 73.5% |
| IP 주소 | 84/85 · 98.8% |
| 비밀번호 | 한국어 표본 23/26 · 88.5%; 비밀정보 표본 4/30 · 13.3% |
| 사업자번호 | 0/26 |
| API 키 | 14/30 · 46.7% |

비밀번호 결과는 데이터 출처와 표현 방식에 따라 크게 달랐다. 서로 다른 표본의 수치를 합쳐 하나의 성능처럼 제시하면 안 된다.

### 전체 파이프라인 처리시간 및 자원

평가 머신에서 로컬 모델 2개 추론 스레드로 측정했다. 처리시간은 탐지·가명화·재검사 구간이며 모델 최초 로딩은 별도다.

| 표본 | 파이프라인 성공 | 중앙값 | p95 | 최대 |
|---|---:|---:|---:|---:|
| 한국어 510건 | 509/510 | 73.86ms | 149.06ms | 434.59ms |
| 비밀정보 90건 | 89/90 | 85.28ms | 395.13ms | 544.86ms |

- 모델 로딩: 294.4ms
- 프로세스 최대 RSS: 585.1MiB. 요청별 사용량이 아니라 평가 프로세스 누적 최대치다.
- 전체 파이프라인 실패 2건은 두 표본에서 각각 발생한 겹침 구간 가명화 오류다. 실패를 탐지 성공으로 계산하지 않았다.
- CPU 사용률의 장시간 백그라운드 수치는 측정하지 않았다.

## 5. 개선 후보 규칙 실험 — 제품 성능과 분리

후보 규칙은 탐지 원인 분석을 위한 오프라인 실험이다. **현재 테스트 화면이나 제품 탐지기에 연결되지 않았다.**

| 유형 | 기존 규칙 | 후보 규칙 결합 | 해석 |
|---|---:|---:|---|
| 사업자번호 | 0/26 | 26/26 | 이 표본의 사업자번호는 모두 3-2-5 하이픈 형식이지만 체크섬이 유효하지 않았다. 형식만 보는 후보가 잡은 결과이며 일반화 성능은 아니다. |
| API 키 | 14/30 | 23/30 | 제공자별 패턴·설정값 추출을 추가한 규칙 비교 결과다. 7건은 여전히 놓쳤다. |

후보 규칙의 가상 회귀 사례는 10/10 통과했다. 비민감 주석 표본 30건 중 탐지 경고는 기존 1건, 후보 결합 1건이었지만 해당 라벨을 모두 사람이 검증한 것은 아니므로 오탐률로 부르지 않는다.

## 6. 시연 흐름

1. 로컬 테스트 화면에서 가상의 개인정보와 키 설정 예시를 입력한다.
2. 탐지 유형과 가명화 결과, 재검사 결과를 보여준다.
3. 가명이 들어간 가상의 응답을 입력해 이름 등 허용 유형이 현재 작업 매핑으로 복원되는 것을 보여준다.
4. API 키·토큰은 복원되지 않고 가명 상태로 남는 점, 작업 종료 시 매핑이 폐기되는 점을 시연한다.

실제 개인정보나 유효한 API 키를 시연에 사용하지 않는다. 탐지율이 낮은 유형은 결과에서 누락될 수 있음을 함께 안내한다.

## 7. 발표 시 한계와 다음 단계

- 데이터는 실제 기업 입력 분포를 대표하지 않으며, 원본 주석의 정확성을 전수 수동 검증하지 않았다. 모델 학습 데이터와 평가 데이터의 중복 여부도 확인하지 않았다.
- 사업자번호 표본의 체크섬이 모두 무효라, 현재 체크섬 규칙은 해당 라벨 26건을 놓쳤다. 문맥을 이용한 의심 후보 처리와 음성 예시 검증이 필요하다.
- API 키 후보 규칙은 표본에서 개선됐지만 일반형 필드명, 셸 fallback, 문서·로그 표현 미탐과 오탐을 더 평가해야 한다.
- 후보 규칙을 제품 탐지기에 통합한 뒤, 검토된 양성·음성 평가셋에서 유형별 정밀도·재현율·F1과 마스킹 잔존률을 다시 측정해야 한다.
- 백엔드 로그/큐 모듈과 AI 모듈은 별도 구현이다. 현재 요청 데이터 계약과 end-to-end 통합은 완료되지 않았다.
- CC BY-NC 4.0 비밀정보 표본은 비상업적 조건이 표시되어 있다. 상업적 이용 전 원출처별 라이선스를 확인한다.

## 발표용 30초 설명

"사용자가 AI에 입력하기 전, 개인정보를 컴퓨터 안에서 규칙과 로컬 ONNX 모델로 찾아 가명으로 치환하는 MVP를 만들었습니다. 600개 문장 평가에서 전화번호와 이메일은 각각 96.8%, 100%의 정답 구간 전체 탐지율을 보였지만, 사업자번호는 0%, API 키는 46.7%로 개선이 필요했습니다. 데이터는 합성·공개 표본이라 실제 기업 성능을 보장하지 않습니다. 원문 매핑은 작업 중 메모리에만 두며, 비밀번호와 API 키는 응답에서 원문으로 복원하지 않습니다."
